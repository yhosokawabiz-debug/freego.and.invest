## 1. 背景と目的

### 1.1 現状

ライトスタッフ社は以下 4 チャネルで販売している。

| # | チャネル | 受注の入口 | 顧客データの自社利用 |
|---|---|---|---|
| 1 | Amazon | Seller Central | 不可（規約上） |
| 2 | 楽天市場 | RMS | 不可（メールはマスク） |
| 3 | 自社サイト | カラーミーショップ（right-net.shop-pro.jp） | 可 |
| 4 | DM（会員向け定期送付）→ 電話・ハガキ・FAX 受注 | オペレーター手入力 【要確認：入力先システム】 | 可 |

後工程（現行）:

```
4チャネル → ネクストエンジン（受注集約）
          → テープス（キャンペーン同梱物の自動付与）
          → 後払い.com API（与信）
          → 出荷可能リスト → 外部 WMS → 出荷
          → 送り状番号を NE へ戻す → 各モールへ出荷通知
```

### 1.2 課題（仮説）

1. 自社顧客（Web 会員と DM 会員）の情報がばらばらで、名寄せ・LTV 分析・クロスチャネル施策ができない。
2. 電話・ハガキ受注の入力画面がパッケージ（カラーミー/NE）頼みで、会員価格・媒体コード・定期などの業務ルールを柔軟に扱えない。
3. 同梱物ルールがテープス内に分散していて、全体が見えない。
4. SaaS を直列につないでいるため、変更のたびに複数社の制約を受ける。

### 1.3 目的

- **自社顧客（Web + DM）の顧客基盤を一つにまとめ**、LTV を最大化する。
- 業務ルール（価格・キャンペーン・同梱・定期）を**自社でいつでも変えられる**状態にする。
- 自社 WMS「ロジスタ」と直結し、受注から出荷まで自社がコントロールできる範囲を広げる。

### 1.4 スコープの基本方針

- **自社で作る**：顧客・会員基盤、自社 EC フロント、電話受注画面、価格・キャンペーン・同梱ルール、定期購入、DM 施策管理、分析。
- **外部サービスを使う**：カード決済（PSP のトークン決済）、後払い与信（後払い.com）、メール配信基盤、配送キャリアの送り状発行（WMS 経由）。
- **当面は残す**：ネクストエンジン（モール受注の集約・モールへの出荷通知）。将来置き換える余地を残した設計にする（`OrderHub` 抽象。7.2 参照）。

## 5. ドメインモデル（主要エンティティ）

```
Customer ──< Address
   │  ├──< ContactConsent（DM/メール/電話の同意と履歴）
   │  ├──< CustomerNote（対応履歴）
   │  └──< CustomerMerge（名寄せ履歴）
   │
   ├──< Order ──< OrderLine ──> Sku
   │      │  ├──< OrderAdjustment（値引・送料・適用ルール）
   │      │  ├──< OrderBundleItem（同梱物）
   │      │  ├──< Payment ──< PaymentTransaction
   │      │  ├──< Shipment ──< ShipmentLine
   │      │  └──< OrderStatusHistory
   │      └── source: channel / mediaCode / subscriptionId
   │
   ├──< Subscription ──< SubscriptionLine
   │      └──< SubscriptionEvent（変更・スキップ・解約）
   │
   └──< DmDelivery ──> DmCampaign（媒体コード）

Product ──< Sku ──< Price（種別・期間・条件）
Sku：kind = sellable | bundle_insert | set
CampaignRule（条件 JSON / アクション JSON / 優先度 / 期間）
IntegrationJob（連携ジョブの状態・リトライ回数・ペイロード）
AuditLog
```

- 金額は**整数（円）**で持つ。浮動小数点は使わない。
- 税は明細ごとに税率を持ち、端数処理のルールを一箇所にまとめる（設定値。【要確認：切捨/四捨五入】）。
- 外部 ID（NE 伝票番号・後払い.com 取引 ID・PSP 取引 ID・ロジスタ出荷 ID）は専用カラムで持ち、ユニーク制約を付ける。

## 6. 受注ステータス遷移

```
DRAFT（一時保存）
  └▶ RECEIVED（受付）
        ├▶ PAYMENT_PENDING（与信待ち）
        │     ├▶ AUTHORIZED ─────────────┐
        │     ├▶ AUTH_HOLD（保留：要対応）─┤（対応後に再与信）
        │     └▶ AUTH_REJECTED ─▶ CANCELLED / 支払方法変更で再与信
        └（代引きは与信をスキップ）───────┤
                                         ▼
                                  READY_TO_SHIP（出荷可能）
                                         ▼
                                  SHIP_REQUESTED（OrderHub/WMS へ送信済）
                                         ▼
                                  SHIPPED（出荷済：送り状番号あり）
                                         ▼
                                  COMPLETED
  どの状態からでも（出荷前なら）▶ CANCELLED
  SHIPPED 以降 ▶ RETURN_REQUESTED ▶ RETURNED / EXCHANGED
```

- 遷移はドメイン層の一箇所（状態機械）で定義し、不正な遷移は例外にする。
- 外部連携は「状態遷移 → アウトボックスにイベントを書く → Worker が送信」の形にする（トランザクションアウトボックス）。

## 7. 外部連携

### 7.1 一覧

| ID | 連携先 | 方向 | 内容 | フェーズ |
|---|---|---|---|---|
| IF-01 | ネクストエンジン API | 送信 | 自社チャネルの確定受注を受注伝票として登録【要確認：API の受注アップロードを使うか、汎用カート連携にするか】 | 1 |

| IF-03 | ネクストエンジン API | 受信 | モール受注（分析用・読み取り専用） | 2 |

| IF-05 | PSP（GMO-PG / SB ペイメント等【要確認】） | 送受信 | トークン決済・3DS・与信・売上確定・取消・カード預かり | 1 |

### 7.2 連携設計の原則

- 外部サービスごとに **Gateway インターフェース**（`OrderHubGateway` / `AtobaraiGateway` / `PaymentGateway` / `WmsGateway`）を定義し、本番実装・**モック実装**・サンドボックス実装を差し替えられるようにする。
- `OrderHubGateway` は「ネクストエンジン実装」と「ロジスタ直結実装」を切り替えられる設計にする（Phase 3 で物流はロジスタ直結、モールは NE、という併用ができること）。
- すべての送信は**冪等**にする（外部 ID・冪等キーで二重登録を防ぐ）。
- 失敗したら指数バックオフで再試行し、上限を超えたら `IntegrationJob` を FAILED にして管理画面に出す（FR-1004）。
- API 仕様が確定していない連携先（ロジスタ・後払い.com の詳細）は、**まずモックと契約テストを作り**、仕様が確定したら本番実装を足す。

| ID | 区分 | 要件 |
|---|---|---|
| NFR-01 | 性能 | ストアフロントの主要ページは p95 で 1.5 秒以内（サーバー応答 500ms 以内）。受注入力画面の顧客検索は 300ms 以内 |
| NFR-02 | 規模 | 想定値【要確認】：顧客 数十万件 / 受注 日 数百〜数千件 / SKU 数百〜数千。この 10 倍まで設計変更なしで扱えること |
| NFR-03 | 可用性 | ストアフロント・受注入力は月間 99.9%。メンテナンスは深夜帯に告知して実施 |
| NFR-04 | セキュリティ | カード情報を通さない・保存しない（割賦販売法・PCI DSS の対象範囲を最小にする）。OWASP Top 10 対策。管理画面は MFA 必須・接続元 IP の制限を設定可能にする |

| NFR-06 | 監査 | 操作ログは 3 年以上保存【要確認】。受注・決済関連の記録は税法上の保存期間（7 年）に従う |

| NFR-08 | 運用監視 | エラー率・連携の失敗・ジョブの滞留を監視して通知する。出荷締め時刻の前に未連携の受注があれば警告する |
| NFR-09 | アクセシビリティ | ストアフロントは WCAG 2.1 AA を目標にする。文字サイズを切り替えられるようにする |
| NFR-10 | 対応端末 | ストアフロント：スマホ優先＋PC。管理画面：PC（1366px 以上） |
| NFR-11 | 保守性 | ドメインロジックのユニットテストのカバレッジ 80% 以上。外部連携は契約テストで担保 |
| NFR-12 | 法令 | 特定商取引法（最終確認画面・表記ページ）、景品表示法、薬機法（健康食品・化粧品の場合）、インボイス制度、電子帳簿保存法 |

## 9. フェーズ計画

**基本方針：一度に全部を切り替えない。各フェーズの終わりで業務が回る状態にする。**

### Phase 1（MVP）：顧客基盤＋電話受注＋自社 EC（カラーミー撤退）

- 顧客・会員基盤（FR-101〜110, 112）
- 商品・価格（FR-201〜206, 208）
- 電話・ハガキ受注入力（FR-401〜408）
- ストアフロント（FR-301〜305, 307〜312, 314）
- 定期購入（FR-601〜605, 607）
- 受注管理・NE 連携（FR-701〜705, 707）
- 決済：カード（PSP）・後払い（NE 経由）・代引き（FR-801〜806）
- DM 施策管理の基本（FR-901〜905）
- 管理機能（FR-1001〜1004）
- カラーミーからのデータ移行（IF-09）

**Phase 1 完了の条件**：カラーミーを止めて、自社チャネルの受注がすべて LS-Commerce → NE → 現行 WMS の流れで出荷できること。同梱物の付与はテープスのまま。

### Phase 2：分析と CRM の強化

- モール受注の取り込み（分析用）、ダッシュボード、RFM・コホート分析（FR-706, 906, 907）
- 会員ランク（FR-108）、CMS 承認フロー（FR-207）、のし・ギフト（FR-306）

### Phase 3：キャンペーンエンジン＋ロジスタ直結

- キャンペーン・同梱ルールエンジン（FR-501〜506）→ テープスを止める
- 後払い.com と直接連携（IF-04）
- ロジスタ連携（IF-06）。**現行 WMS と並行稼働してから切り替える**（一部 SKU または一部チャネルから）

### Phase 4（検討）：ネクストエンジン置き換え

- Amazon SP-API・楽天 RMS を直接取り込み（IF-10）。費用対効果を見て判断する

## 12. UX 方針（ストアフロント）
